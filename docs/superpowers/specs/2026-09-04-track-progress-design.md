# Дизайн: индикатор позиции трека (прошло/всего) в терминале

Дата: 2026-09-04
Статус: согласован с пользователем

## Контекст и проблема

`yam` — терминальный плеер радиостанций Яндекс Музыки. Сейчас во время
воспроизведения в терминале виден только заголовок трека
(`[N] artist — title`) и единичные сообщения (`[пауза]`, `[избранное]`).
Не видно, сколько трек уже идёт и какова его общая длина.

Пользователь хочет индикатор вида `00:00/00:00`, отображаемый прямо в
терминале **в одной строке** и обновляемый на месте.

Согласованные решения:
- формат — **«прошло / всего»** (классика плеера: `01:23 / 03:42`);
- строка индикатора — **под заголовком трека**, перерисовка через
  carriage return (`\r`), без создания новых строк.

## Цель

Показывать реальную позицию воспроизведения в mpv (`time-pos`) и общую
длительность трека, обновляя одну строку в терминале раз в ~0,5 с.

## Scope (границы)

Входит:
- Опрос mpv через существующий JSON IPC-сокет (`get_property`).
- Строка вида `  01:23 / 03:42` (формат `mm:ss`, для треков длиннее часа
  `h:mm:ss`), обновляется на месте.
- Корректное переплетение с существующими сообщениями плеера через общий
  мьютекс: сообщение сначала «очищает» строку индикатора, затем печатается.
- Индикатор гаснет (строка очищается) при конце/пропуске трека, до печати
  заголовка следующего.
- При перенаправлении stdout в файл (не tty) индикатор не выводится, чтобы
  в лог не попадал поток `\r`.

Не входит (YAGNI, отдельными шагами при желании):
- Push-режим `observe_property` (опроса 0,5 с достаточно).
- Прогресс-бар (символьная полоса), проценты, «осталось N сек».
- Изменение заголовка трека и иных сообщений.

## Детали реализации (только `yam.go`)

### 1. `mpvGetProps(sock string, props []string) (map[string]float64, error)`

Опрос свойств mpv через одно короткое unix-соединение (стиль существующего
`mpvCmd`, yam.go):
- `net.DialTimeout("unix", sock, 500ms)`; дедлайн соединения 2 с.
- Каждое свойство шлится как
  `{"command":["get_property",<prop>],"request_id":<i>}` (разные request_id).
- Ответы читаются строками; события mpv без `request_id` (например
  `end-file`) просто пропускаются.
- `error == "success"` и `data` — число → записываем в map.
  `data == null` (длина ещё не определена) — property отсутствует в map.
- Ошибка (mpv умер, таймаут) — возвращаем то, что успели получить, и `error`.

Используемые свойства: `time-pos` (позиция, сек) и `length` (длительность,
сек).

### 2. `progressUI` — горутина-тикер на время жизни одного трека

```
type progressUI struct {
    mu    sync.Mutex   // сериализует вывод тикера и сообщений
    sock  string
    total float64      // fallback: track.DurationMs / 1000
    live  bool         // stdout является tty
    stop  chan struct{}
    done  chan struct{}
}
```

- `newProgressUI(sock, total)`: `live = true`, только если `os.Stdout`
  — char-устройство (та же проверка, что в `setCBreak`).
- `start()`: если `live` — `go run()`, иначе сразу `close(done)`
  (все методы no-op для не-tty).
- `stop()`: `close(stop)` + ожидание `<-done`. Гарантирует, что тикер
  физически прекратил писать до возврата из `playOne` — заголовок
  следующего трека не будет «затёрт» поздним тиком.
- `run()`: тикер 500 мс. На каждый тик:
  - `mpvGetProps(sock, ["time-pos","length"])`; ошибка/нет `time-pos` →
    тик пропускается (вывод не трогаем).
  - `total = length из mpv`, если `> 0`; иначе fallback `track.DurationMs`.
  - `render(pos, total)` под мьютексом:
    `\r` + строка + пробелы до 24 символов (стирает остатки прошлой строки).
- `clear()` под тем же мьютексом: `\r` + 24 пробела + `\r`
  (возвращает курсор в начало строки, строка индикатора «исчезает»).
- Формат времени — `fmtClock(sec)`: `mm:ss`, при `h > 0` → `h:mm:ss`;
  отрицательные значения → 0.

### 3. Встраивание в `playOne` (yam.go)

- После ожидания появления IPC-сокета (существующий цикл 100×50 мс):
  `pg := newProgressUI(sock, float64(tr.DurationMs)/1000)`, `pg.start()`,
  `defer pg.stop()`.
- Все `fmt.Print*` внутри `playOne` (`[пауза]`, `[продолжить]`,
  `[избранное] ...`) заменяются на локальный хелпер:
  ```
  note := func(format string, args ...any) {
      pg.clear()
      fmt.Printf(format+"\n", args...)
  }
  ```
  Сообщения и тикер больше не пересекаются: и то, и другое идёт под
  одним мьютексом, и сообщение всегда начинается с новой строки.
- Конец трека (любой выход из `playOne`): `defer pg.stop()` чистит строку
  и дожидается выхода горутины — заголовок следующего трека в `run()`
  печатается на чистом терминале.
- Пауза: `time-pos` у mpv замирает сам — строка «замирает» автоматически,
  спецкода не нужно.

### 4. README

- В «Возможности» — пункт: индикатор «прошло/всего» обновляется в одной
  строке терминала.

## Поведение и сценарии

- Старт трека: под заголовком появляется `  00:00 / 03:42` и тикает.
- Пауза (`1`): позиция замирает; при возобновлении — продолжается.
- Пропуск (`2`): строка индикатора гаснет, печатается заголовок нового трека.
- `q` / Ctrl+C: строка гаснет, выход как сейчас.
- Длина mpv не определена (early buffering): показываем `DurationMs` из API.
- Вывод в файл / pipe: индикатор отключается, остальной вывод не меняется.
- mpv умер нештатно: тики просто не обновляются (dial ошибка → пропуск).

## Тестирование / верификация

- `go build -o yam .`, `go vet ./...`, `gofmt -l .` — чистые.
- Живой прогон ~15 с под pty: тик обновляется каждую секунду; `1` —
  пауза/продолжить (позиция замирает/идёт дальше); `2` — следующий трек,
  индикатор перезапускается с 00:00; `q` — чистый выход, строка не
  «залипает».
- `./yam --check` — smoke-тест без звука не изменён.

## Риски

- mpv шлёт события на все IPC-соединения — чтец `mpvGetProps` обязан
  пропускать строки без известного `request_id` (учтено в п. 1).
- Две параллельные горутины пишут в stdout (тик + сообщения) — сериализация
  обязательна (мьютекс в п. 2).
- При очень узком терминале строка индикатора (≤24 символа) всё равно
  помещается; при переносе строк `\r`-перерисовка остаётся в пределах
  строки вывода.
